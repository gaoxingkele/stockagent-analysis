## 裁决与后续

这两个现存批次的历史特征可得性 **未通过**。因子收件发生于2026年，且行情依赖缺收件绑定；不能据此将2024年样本当作已证实时点正确的训练输入。现存样本全部保留，未知不转负例，不缩成未来完整子集，也不修改正式 H01 状态冒充验收。

下一步分开处理：

1. 追溯日线实际生成/导入来源及已存在的版本归档；只接受能绑定所用字节与当时可得时间的证据，当前重采不能修复旧时点。
2. 对派生候选、特征、标签分别展开依赖，区分原始收件、派生计算时间与目标成熟时间；收件晚于信号日的标签并不自动构成泄漏，关键是它是否早于实际训练截止点。
3. 若限定来源调查后仍不可证实，提交明确的范围/协议选择，不擅自以可得时间假设放行；可继续开发正式阶段验收接口，但不能以合成测试替代历史有效性。

本轮仅取证与裁决，没有训练、重采、生产修改或完整测试重跑。冻结预算、O/P/T 定义及 G3 均不变。

## 补充：派生日线到原始缓存的追溯

继续检查 causal_price_features 与 factor_price_features 的实际消费代码后澄清：上表的21个 daily 输入是 identity-panel 的 canonical 分区，不是直接供应商文件。不能要求 canonical 分区具备供应商收件记录，也不能仅凭没有直接匹配就断言其原始依赖没有证明。上一轮措辞应按本节解释。

本轮沿 identity-panel-a8199bfc7f2143ba8e5f4953ff088e55 的 `inputs_outputs.json` 展开到真实 `output/tushare_cache/daily`。核验面板 summary 固定哈希，以及映射文件 SHA256 `a61611a310837b71f03bfb9fe211c742e3b44418622f30fb54173826c9961991`；两个窗口合并为26个唯一分区（20240524–20240701），其 canonical 与 raw 文件均逐一重新核对匹配声明哈希。26个原始文件的同名 JSON 收件记录为0；`git ls-files output/tushare_cache` 与 `git log --all --oneline -- output/tushare_cache/daily` 没有记录。

因此，已证实的是“原始缓存→派生日线”的字节引用链；未证实的是“原始缓存所用版本何时已被取得”。没有本轮重新计算身份映射、没有证明原始供应商历史版本真实性。

补读 bootstrap_tushare_cache.py、fetch_tushare_daily_bulk.py、daily_review.py 的写入路径，均直接保存 parquet、没有原始收件/哈希记录。其运行日志或当前源码不能认证现存全部文件的历史生成过程。本地已知采集路径、Git与已登记外部目录的有限调查到此未找到可以补足旧时点的证据；没有据此宣称遍历全部磁盘或外部备份。

裁决：不再重复扫描上述相同路径或重采相同历史数据来尝试通过时点门槛。若要使这两个批次通过当前严格历史时点协议，需要额外的原始版本归档/可得时间证据；若改用“回溯数据、可得性未证实”的研究假设，必须独立标注并获得协议变更，不属于原 H01 通过。未来真实采证也不能倒填这26个旧文件的收件时间。其余正式接口开发仍可继续，但不能以此宣告全 harness 已完成。
