# S20-Pure 2026 Q4 工作计划：补数据、拆收益、加信息、管住研究流程

制定：2026-10-01｜依据：`wiki/2026-09-30_theory-audit-and-roadmap.md`｜当前生产：R20 池 A；影子：S20 进攻版 + 阀门 B、稳健版

## 0. 目标与总纪律

**目标**：提高每日 Top20/30 的"安全且上涨"质量（先跌破 −10% 的比例更低、成功率更高、每笔期望更高），并且**弄清楚收益从哪来**（是不是主要来自小盘）。

**所有工作流共用的纪律**（沿用本仓反过拟合脚手架）：
1. 先写经济假设，再写代码；没有假设的因子不进评估。
2. 参数只在开发期（2025-03～2026-01 的测试折）选；2026-01-27～08-05 已消费，只作描述；**2026-08-06 以后是唯一干净的样本外**。
3. 每个学习式改进都要有朴素对照（例如"按波动率截同样比例"），输给朴素就不用。
4. 每个结论同时报：每笔期望、成功率、先破 −10% 比例、最差月、扣 CH-3 风格后的 alpha、容量（成交额约束）。
5. 改动先冻结、后测试；每轮写 wiki。

## 2. 风格审计与消融（第 1～2 周）——回答"收益是不是来自小盘"

先说明：**"主要收益来自小盘"目前还是假设，没有量过**。这一步就是要把它量出来，并把三类因素分开。

### 2.1 暴露审计（不改模型，只测量）
对 R20 池 A、S20 进攻版、进攻版+B、稳健版、全市场，逐日计算名单的：
- 市值（总市值、流通市值）分位
- 估值（EP、BP）分位
- 换手率分位、成交额（交易量）分位
- 波动（natr）、MAX（20 日最大单日涨幅）

**交付**：按月的暴露热力图 + 汇总表。

### 2.2 收益归因
- 按 Liu–Stambaugh–Yuan（2019）构建 A 股 CH-3（市值、EP 价值；剔除最小 30% 壳价值污染）和 CH-4（加换手/情绪因子）。
- 名单日收益对这些因子回归：截距 = 扣除风格后的 alpha；同时看各因子载荷。

### 2.3 三类因素的单独消融（你提的方向，设计成"三类 × 三种做法"）
三类因素：**A 交易量/成交额**，**B 市值/估值**，**C 换手**。

| 做法 | 怎么做 | 回答的问题 |
|---|---|---|
| ① 特征消融（模型层） | stage1 用原配方重训，分别去掉 A / B / C 各自的特征组（以及全部去掉），开发期三折比较 | 模型的排序能力有多少来自这一类信息 |
| ② 名单中性化（组合层） | 在每个分位桶内选股（例如按市值 5 分位各取 4 只），或者剔除最小 30% 市值 | 去掉这类暴露后，名单还剩多少收益 |
| ③ 加回（反向） | 把 B 类（市值、估值）作为显式特征加回 stage1 | 显式给出风格信息，是否改善或只是放大暴露 |

外加 **容量检验**：按成交额设门槛（例如日均成交额 ≥ 1 亿 / 3 亿），看收益如何衰减，估算可承载的资金规模。

**决策规则（事先登记）**：
- 如果中性化后每笔期望下降超过一半 → 收益主要是风格暴露；方案改为"显式控制风格 + 只在风格内部选股"，并按容量重新定位。
- 如果扣 CH-3 后 alpha 仍显著（按月 bootstrap 区间不含 0）→ 保留现有结构，风格作为风险控制而不是收益来源。

**交付**：`scripts/style_audit.py`、`scripts/ablation_style_families.py`、wiki 一篇。

## 3. 策略与因子库优化（第 2～4 周）

每个候选都按"假设 → 朴素对照 → 开发期 → 预登记 → 影子"的流水线走。按理论把握排序：

| 候选 | 经济假设（出处） | 用在哪一层 | 朴素对照 |
|---|---|---|---|
| MAX（20 日最大单日涨幅） | 彩票股效应，散户市场更强（Bali 2011；中国证据） | 振幅上限的第二维度 | natr 截断 |
| 分析师预期修正（`report_rc`） | 盈利预期上修的股票后续跑赢（分析师修正动量） | **方向**轴，第一个有理论支撑的方向信号 | 无修正样本 / 随机 |
| 解禁压力、减持公告、高质押 | 供给冲击与内部人卖出 → 下跌风险 | 排雷硬门 | 不排雷 |
| 财报窗口 + 业绩预告下修 | 盈利公告前后的跳空风险 | 排雷 / 降权 | 不处理 |
| 质量（ROE、负债率） | 质量溢价，暴雷概率更低 | 稳健版的排序辅助 | 无 |
| 风格显式控制（市值、EP、换手） | CH-3/CH-4 | 视第 2 节结论而定 | — |

**阀门 v2**（单列，理论最明确）：
- 连续调仓：当日仓位 = 目标波动 ÷ 近期市场波动，上限 100%（Moreira–Muir 2017；中国 2024 年证据）。
- 区分恐慌阶段：跌停家数高位**且仍在上升**才降仓；高位**已回落**视为恐慌尾声，不降仓（Daniel–Moskowitz 2016）。
- 用 2015 年以来的长历史做（约 100 个以上独立窗口），然后在 08-06 以后的新数据上前瞻验证。

**交付**：每个候选一页结论（通过 / 否决），通过的进入 v1.2 预登记合约。

## 4. 新闻与重大信息披露：LLM + Jev（第 2 周起，持续）

**信息源**（按可得性）：
1. `major_news` 市场要闻（有权限）→ 市场级方向 / 风险，接入阀门。
2. `report_rc` 研报标题与评级变化（有权限）→ 个股方向。
3. 结构化事件（解禁、减持、质押、预告）→ 排雷，不需要 LLM。
4. 个股新闻、公告全文：需要升级 Tushare 积分，或验证 AKShare 东财个股新闻/公告的覆盖与时间戳。

**分工**：
- **大模型（Claude 等）**：抽取事件、归类（利好/利空/中性）、摘要，产出结构化字段。
- **Jev**：对结构化后的状态做类型化判断（例如"未来 5 日出现利空冲击的概率"），输出 0–1 概率，作为经典模型的特征。之前的教训：Jev 本身不带信息，**给它的文本必须是真正影响市场的文本**。

**评估纪律**：
- 历史回测必须带四组对照：真实日期、错配日期、错配文本、只给数字；并与"同数字免费模型"比较。
- 主证据来自**前瞻记录**：从现在起每天带时间戳保存文本、LLM 输出和 Jev 输出。
- 验收指标：池内逐日方向 AUC、排雷后"先破 −10%"比例的下降、以及相对朴素对照的增量。

**成本预算**：Jev 每天 ≤ 200 次（候选池 100 只 × 2 种问题）；LLM 抽取按候选池而非全市场。

## 5. Alpha 智能体探索（第 3～6 周）

借鉴 AlphaAgent（KDD 2025）和 R&D-Agent-Quant（NeurIPS 2025），在本仓搭一个**受约束**的因子研究循环，用 Claude Code 的子智能体 / 工作流来编排：

| 角色 | 做什么 | 约束 |
|---|---|---|
| 假设智能体 | 根据文献、wiki 里的否定记录、现有数据字段，写出经济假设和因子表达式 | 必须引用机制；不得重复 wiki 里已否定的方向 |
| 实现智能体 | 用受限的表达式语言（只允许现有字段和固定算子）实现因子 | 复杂度上限（算子数、窗口数） |
| 评估器（固定代码，不是智能体） | 开发期 IC、按 regime 拆分、与现有因子的相关性/表达式相似度、朴素对照、换手与成本 | 评估规则冻结，智能体不能修改 |
| 审查智能体 | 检查假设与因子是否一致、是否在偷看数据 | 不一致直接否决 |
| 记忆 | 每个尝试和结论写入登记表与 wiki | 记录总尝试次数，用于多重检验校正（deflated Sharpe） |

**关键设计**：
- 08-06 以后的数据对智能体完全不可见，只有人工在阶段末一次性开封。
- 统计门槛随尝试次数提高（Harvey–Liu–Zhu 2016 的思路）。
- 产出的不是"上线因子"，而是进入第 3 节流水线的**候选**。

**可选**：评估微软 RD-Agent（开源，基于 Qlib）能否直接接入我们的数据格式；如果接入成本高于自建，就只借鉴它的流程。

## 6. Kronos（暂缓，记录事实）

- 开源（MIT），Hugging Face `NeoQuasar/Kronos-mini/small/base`，参数 4.1M / 24.7M / 102.3M；上下文 2048 / 512 / 512。
- **没有官方在线 API**，只有一个 BTC/USDT 的演示页面。
- 显存：base 版权重约 0.4GB（fp32），推理 2–4GB 显存的 GPU 即可；CPU 也能跑，但全市场 5000 只每天推理会慢，需要批处理。
- 注意区分：亚马逊的 Chronos 是另一个通用时间序列模型，不是这个。
- 若以后启用：用途定位为**波动预测**（服务振幅上限和阀门），不用于方向。

## 7. 运行与评估（贯穿全程）

- **每日自动化**：拉 Tushare → 重建特征 → stage1 打分 → 名单 → 阀门 → Jev/LLM 前瞻记录 → **保存当日发布名单**（R20 与 S20）。
- **每周报告**：滚动 20 日的成功率、先破 −10%、每笔期望，对比 R20 与全市场。
- **决策关口**：约 11 月下旬，08-06 以后满 60 个成熟交易日，用 `compare_r20_vs_s20_pure.py --published` 和重放数据做正式评审。
